Validation against PyG¶

mlx-graphs follows PyTorch Geometric (PyG), and every layer, sampler and model added for PyG parity was checked against PyG: layers by copying PyG's weights and comparing outputs and gradients, samplers statistically, and models by training them in both frameworks on the same data. This page describes how, summarizes the results, lists the bugs these checks found, and shows how to rerun them.

The full result tables are in the repository, under benchmarks/quality. The speed comparison is on the Benchmarks page.

Method¶

The checks work at three levels:

Level What is compared Where
Layers The same layer is built in both frameworks and PyG's weights are copied into the mlx-graphs one. Both run on the same random graph, with duplicate edges, self-loops and isolated nodes, and the outputs (and for many layers the gradients) must agree. The unit tests, tests/
Samplers and loaders Exact comparisons with PyG's pure-Python code paths where they exist, and otherwise statistical properties: coverage of every node once per epoch, uniform neighbour sampling, unbiased normalizations. Then mini-batch training against full-batch training. benchmarks/quality/sampler_quality.py
Training quality The same model is trained in both frameworks, with the same data, splits and hyperparameters, over several seeds. The test metric is read at the epoch of best validation metric. benchmarks/quality/node_quality.py, benchmarks/quality/graph_quality.py, and the TGN, GPS and to_hetero comparisons

A training configuration passes when the gap between the means is within 1 point, or within 2 standard deviations of PyG's results: \(|\mathrm{gap}| \le 1\) or \(|\mathrm{gap}| \le 2\,\sigma_{\mathrm{PyG}}\). The node classification table also marks pass (noise) a gap within 2 standard errors of the difference of the means.

Keeping the comparison fair

  • Same model and data. Both frameworks train the same architecture with the same hyperparameters, on identical arrays: the data is loaded once and handed to both, and the splits are the same. Each framework keeps its own default initialization, and mlx-graphs layers are initialized as in PyG.
  • Adam's bias correction. MLX's Adam is created with bias_correction=True, which is the update rule of torch.optim.Adam. MLX's default has no bias correction and takes much larger first steps: it lowered GAT's accuracy on Cora by about 4 points in the speed benchmarks, and gave GPS on Peptides-func a clearly higher training loss.
  • L2 penalty vs weight decay. torch.optim.Adam(weight_decay=...) adds weight_decay * p to the gradients (an L2 penalty), which is not the decoupled weight decay of AdamW. The harnesses reproduce it in MLX by adding the same term to the gradients. Where the PyG script uses AdamW (the to_hetero comparison), both frameworks use AdamW.
  • Devices. mlx-graphs runs on the GPU and PyG on the CPU (with one or two torch threads per run), except for the slow deep models of the node classification harness (GCNII, DeeperGCN), for which PyG runs on MPS. The device changes the speed, not what is compared.
  • One process per run. Every configuration and seed runs in its own process under a memory cap.

Numerical tolerance

MLX's float32 matmul on the Mac's GPU has a relative error of about 1e-3, where NumPy and torch on the CPU have about 1e-7. This is MLX behaviour, not mlx-graphs', and it is the source of the ~1e-3 differences of the forward passes. It can be larger for gradients that go through a cancellation: EdgeConv's first layer, whose inputs are differences x_j - x_i, has gradient differences of up to about 10 %. The layer tests therefore use a tolerance of 2e-2: a wrong formula is off by far more. It did not change any training result.

Some layers were also checked with copied weights on full datasets:

  • On Cora: PairNorm, GraphNorm and GENConv (with and without MessageNorm) agree with PyG to GPU matmul precision, forward and input gradients; CorrectAndSmooth agrees to 3e-5; LabelPropagation gives identical accuracies.
  • On PubMed: PNAConv's output and input gradients agree with PyG's to 1e-4 and 1e-8 (relative ~1e-3).
  • On DBLP: the HGT model's forward pass matches PyG's on the full graph.
  • On Peptides-func: the full GPS model gives the same train-mode loss (0.70363 vs 0.70362 on 16 graphs) and gradients within ~1 %.

Point clouds on ModelNet10¶

PointNet++ (PyG's examples/pointnet2_classification.py: fps, radius, PointNetConv) trained for 5 epochs on ModelNet10, on the same fixed clouds of 1024 points sampled through mlx-graphs' ModelNet and SamplePoints, reaches a test accuracy of 80.9 % in mlx-graphs and 82.5 % in PyG (best epoch: 80.9 % and 82.9 %), with training losses of 0.26 and 0.31. DGCNN (DynamicEdgeConv, PyG's examples/dgcnn_classification.py) reaches 78.0 % and 80.2 % after 3 epochs. The point cloud layers, fps, voxel_grid, nearest, graclus and the point cloud transforms are also compared with PyG in the test suite (fps picks the same points as PyG with random_start=False, in 1.9 ms with its Metal kernel against 132 ms for torch_cluster on the CPU, for 32 clouds of 1024 points). Full table: pointcloud_results.md.

Samplers and loaders¶

PyG's own neighbour samplers, GraphSAINT, ShaDow, ClusterData and knn / radius need compiled extensions (pyg-lib, torch_sparse, torch_cluster), so the samplers are checked against references that don't:

  • Exactly, in the test suite: RandomNodeLoader, ClusterLoader, DynamicBatchSampler and ImbalancedSampler against PyG's pure-Python classes; ShaDow subgraphs and full-fan-out NeighborLoader against PyG's k_hop_subgraph; knn / radius against SciPy's KD-tree; KNNGraph / RadiusGraph against PyG's transforms.
  • Statistically: every seed node or item covered exactly once per epoch (NeighborLoader, LinkNeighborLoader, ShaDowKHopSampler, RandomNodeLoader, ClusterLoader); uniform neighbour sampling (chi-squared tests on the highest-degree nodes of Cora); class balance of ImbalancedSampler; batch budgets of DynamicBatchSampler; and the bias of GraphSAINT's normalizations.
  • By training: a 2-layer GraphSAGE trained with each mini-batch method against full-batch training.

Every mini-batch method lands within one standard deviation of full-batch training (test accuracy in %, 5 seeds):

Training Cora PubMed
Full batch, PyG 80.3 ± 0.7 76.9 ± 0.8
Full batch, mlx-graphs 80.2 ± 0.7 77.3 ± 0.8
NeighborLoader [10, 10] 80.3 ± 0.9 76.6 ± 0.4
GraphSAINTRandomWalkSampler 80.3 ± 1.1 77.0 ± 0.9
ClusterLoader (20 parts, 5 per batch) 79.4 ± 1.4 76.9 ± 0.6
ShaDowKHopSampler (depth 2, 10) 80.2 ± 0.8 76.9 ± 0.5

For link prediction, LinkNeighborLoader reaches a test AUC of 84.3 ± 1.4 % on Cora (full batch: 84.4 ± 3.2 % in mlx-graphs, 83.3 ± 1.6 % in PyG) and 89.2 ± 0.7 % on PubMed (full batch: 90.1 % in both). Full results: sampler_results.md.

Large graphs¶

Results of benchmarks/quality/ for the large datasets, temporal neighbour sampling and the memory-mapped feature store (Apple M5 Pro, 64 GB, shared with other jobs, so the times are indicative). Full results: large_graph_results.md.

The datasets are identical to PyG's. dataset_parity.py loads Flickr, Reddit, Reddit2, Yelp, AmazonProducts and PPI with both libraries and compares the edges (in the same order), features, labels and split masks: all equal. PPI is read from the GraphSAGE release (DGL's server, which PyG uses, is down) and gives exactly PyG's 20 / 2 / 2 graphs.

Temporal sampling (temporal_sampler_quality.py, a random graph of 20,000 nodes and 400,000 timestamped edges): with temporal_strategy="last", the mini-batches are identical to PyG's with pyg-lib (8 of 8, with node- and edge-level time); neither library samples an edge later than its seed; with "uniform", the sampling frequencies are as close to uniform as PyG's (mean deviation 0.0267 against 0.0266 with node-level time, no seed rejected by a chi-squared test in either). pyg-lib's C++ sampler is 1.2 to 2.3 times faster than the vectorized numpy one.

to_hetero on DBLP¶

Remaining mismatches¶

Three node classification configurations don't pass.

PNAConv on Cora (-4.6) and CiteSeer (+6.8). The gaps have opposite signs. PNAConv on raw features, with amplification scalers, trains with large loss spikes in both frameworks: PyG's seed 0 on PubMed jumps to a loss of 3.0, and mlx-graphs' seed 3 to 4.9 near the end. With copied weights on PubMed, the layer's output and input gradients agree with PyG's to 1e-4 and 1e-8 (relative ~1e-3): the layer computes the same function, which points to the unstable training rather than to the layer. The PubMed row passes (-0.2), and so do the PNA model on Cora and CiteSeer (+1.7, +3.1) and PNA on MUTAG and PROTEINS.

DirGNNConv(GCNConv) on CiteSeer (+1.8). mlx-graphs is ahead: 68.7 ± 1.4 % against PyG's 66.9 ± 0.7 %, beyond 1 point and twice PyG's small standard deviation. The training losses are close (0.006 / 0.008 over epochs 25-75, 0.011 / 0.008 at the end, PyG / mlx-graphs), the Cora (+0.6) and PubMed (-0.4) rows pass, and with copied weights the layer gives the same outputs as PyG's DirGNNConv (tests/nn/conv/test_dir_gnn_conv.py). No cause has been identified.

Bugs found and fixed¶

Found by the training and sampler comparisons, each fixed with a regression test:

  • SAGEConv with a non-linear aggregation ("max", "min", "std", lists, modules) and more input than output features projected the features before aggregating (max(W x) instead of PyG's W max(x)), a trick only valid for sum and mean. Max error against PyG with copied weights: 1.7.
  • Lists of aggregations: SAGEConv crashed, and GENConv did not accept them. Both now size their projections like PyG's. The other layers with a projection after the aggregation crashed with a shape error, or for GATConv / GATv2Conv returned twice as many rows; they now refuse concatenating lists with a clear error (supports_concat_aggr).
  • NaN gradients from L2 norms at zero in AGNNConv, MessageNorm and GENConv(msg_norm=True): a node whose features are all zero (common after ReLU and dropout) made every gradient NaN. Seen as AGNN on PubMed going NaN at epoch 145, and GENConv with MessageNorm reaching 66 % instead of 79 % on Cora (one seed).
  • MixHopConv stored its per-power layers in a dict that load_weights could not load.
  • AddLaplacianEigenvectorPE did not converge on Cora (float64 eigensolver on float32 values).
  • DirGNNConv(GCNConv(...)), PyG's usual way to build it, raised an error.
  • DirGNNConv(SAGEConv) trained 2-3 points below PyG with twice its training loss: SAGEConv had no root_weight, so both directions kept a root projection. SAGEConv now has PyG's root_weight, and the rows pass (+0.9 / +0.7 / +0.5).
  • TUDataset dropped edge labels (e.g. MUTAG's bond types) and did not reorder edge features with the edges. MUTAG, PROTEINS and NCI1 now equal PyG's arrays.
  • IMDB stored its labels under "movies" instead of the "movie" node type.
  • HeteroDictLinear (used by HGTConv) initialized with Glorot weights instead of torch.nn.Linear's: HGT on DBLP reached 76.9 ± 2.3 % against PyG's 71.8 ± 1.8 %. With PyG's initialization it reaches 73.0 ± 2.5 %.
  • GINEConv's edge projection was also initialized with Glorot weights (GINE on MUTAG: 80.0 ± 10.5 % before the fix, 82.0 ± 7.1 % after, 78.0 ± 13.6 % in PyG).
  • GraphSAINT's edge_norm used the count of the edge's source node, as PyG does, instead of its target (the paper's definition). On Cora, the median relative error of the normalized aggregation was about 50 % with the source count; with the target count it is sampling noise that shrinks with sample_coverage.

Other differences from PyG fixed in the same release (see the changelog):

  • LayerNormalization(mode="graph") gave wrong shapes with batch indices, and mode="node" ignored its own weight and bias. Both now match PyG's LayerNorm.
  • Max and min aggregations gave the full gradient to every tied value (e.g. the identical messages of duplicate edges). They now split it equally, as PyG does.
  • MultiAggregation(mode="std") had a NaN gradient for sets of a single element.
  • GIN and EdgeCNN did not apply the model's act and norm to the MLPs inside their convolutions, as PyG does.

Where mlx-graphs differs from PyG on purpose¶

  • GraphSAINT normalization: target count in edge_norm (see above).
  • GraphSAINT edge sampler: mlx-graphs samples edges with the paper's probabilities, \(1/\deg(u) + 1/\deg(v)\). PyG's GraphSAINTEdgeSampler computes the inverse weighting, which favours edges between hubs. At the same number of edges, the paper's probabilities give a 3.5-4.4x smaller standard deviation of the estimated aggregation.
  • DynamicBatchSampler with skip_too_big=True yields every graph once; PyG re-yields the graphs that follow a skipped one. Without skip_too_big, the batches are the same as PyG's.
  • TGN's LastAggregator gives zeros to nodes without messages, as PyG does with torch-scatter (see above).
  • TopK and SAG pooling break ties between equal scores differently. Both are valid, and training quality is the same.

Reproducing¶

Install the test and benchmark dependencies (some harnesses also use scikit-learn), then run:

pip install -e '.[test,benchmarks]'

# layer-level parity (add --datasets for the slow tests that download data)
pytest tests

# node classification (--configs gcn arma ... for a subset, --summarize for the table only)
python benchmarks/quality/node_quality.py

# graph-level, heterogeneous, link and KG models (--groups tu kge ... for a subset)
python benchmarks/quality/graph_quality.py

# hierarchical and dense pooling on PROTEINS (--models diffpool asap ... for a subset)
python benchmarks/quality/pooling_quality.py

# PointNet++ and DGCNN on ModelNet10 (--models pointnet2 --epochs 5 for a subset)
python benchmarks/quality/pointcloud_quality.py

# SchNet and DimeNet++ on QM9, AttentiveFP on ESOL (--tasks attentivefp for a subset)
python benchmarks/quality/molecular_quality.py

# large graphs: datasets equal to PyG's, GraphSAGE training, temporal sampling, feature store
python benchmarks/run_capped.py --gb 24 -- python benchmarks/quality/dataset_parity.py \
    --data-dir .mlx_graphs_data --datasets flickr reddit2 yelp reddit ppi amazon_products
python benchmarks/run_capped.py --gb 16 -- python benchmarks/quality/large_graph_training.py \
    --datasets flickr --seeds 0 1 2 --epochs 10
PYTHONPATH=<pyg-lib dir> python benchmarks/quality/temporal_sampler_quality.py
python benchmarks/quality/feature_store_memory.py --dir /tmp/fs_bench \
    --num-nodes 1500000 --num-features 1024

# samplers and loaders (about 15 minutes)
python benchmarks/run_capped.py --gb 6 -- python benchmarks/quality/sampler_quality.py \
    --data-dir .mlx_graphs_data --seeds 0 1 2 3 4

# TGN on JODIE Wikipedia
python benchmarks/tgn_comparison/compare.py --data <data_dir> --epochs 8

# GPS on Peptides-func: export the data, train both, check the gradients
python benchmarks/gps_peptides/export_npz.py <data_dir>
python examples/graph_gps_peptides.py --data_dir <data_dir> --epochs 10 --seed 0
python benchmarks/gps_peptides/gps_pyg.py --data_dir <data_dir> --epochs 10 --seed 0
python benchmarks/gps_peptides/grad_parity.py <data_dir>

# to_hetero on DBLP
python benchmarks/to_hetero/compare_dblp.py --data_dir .mlx_graphs_data

Note

The harnesses run every configuration in its own process under a hard memory cap, and kill it above the cap: 6 GB by default for the node and graph harnesses (--memory-gb), 4 GB for the TGN and to_hetero comparisons. The memory is the process' physical footprint, as shown by Activity Monitor, which, unlike RSS, includes the GPU (Metal) allocations of MLX and PyTorch MPS. Run any other script the same way with python benchmarks/run_capped.py --gb <cap> -- <command>. Mini-batches of varying shapes make MLX's buffer cache grow: the sampler harness caps it with mx.set_cache_limit.

The node and graph harnesses append one line per run to node_results.jsonl / graph_results.jsonl and skip the runs already there, so an interrupted run resumes where it stopped.

Not covered¶

  • Training quality on the largest graphs (AmazonProducts, Yelp, ogbn): out of the memory budget of these checks; Flickr and Reddit are covered above. They are part of the speed Benchmarks, which also record accuracy.
  • Mini-batch training in the node classification harness, which trains full batch only. Mini-batch training is checked for GraphSAGE by the sampler harness, and for to_hetero models in mlx-graphs only.
  • PyG's compiled samplers and operations: PyG's neighbour samplers, GraphSAINT, ShaDow, ClusterData (METIS), DynamicEdgeConv and knn_graph need pyg-lib, torch_sparse or torch_cluster, which were not installed. The samplers were checked against references instead, and ClusterLoader was trained with the dependency-free balanced partitioner, not METIS.
  • NCI1 graph classification, which did not fit in the time budget.
  • Converged knowledge graph embeddings: the KGE models trained for 20-40 epochs instead of PyG's 500, so the comparison covers the early training trajectories, not converged models.
  • Attention variants of GeneralConv on CiteSeer and PubMed (Cora only).
  • Compilation: mx.compile for mlx-graphs and torch.compile for PyG.
